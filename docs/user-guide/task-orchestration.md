# Meta 任务编排

任务编排适合能明确交付目标、需要多个阶段或独立验收的项目。规划 Agent 提出计划，用户批准后由工作台调度执行。工作台管理状态、恢复、验收和文件证据，Agent 主要负责业务目标。

## 从对话开始

1. 在已有对话中明确目标，切换到“编排”。对话与编排属于同一任务，继承工作区和用户要求。
2. 新编排默认直接使用当前项目根目录，不新增项目内任务子目录。只有明确选择隔离目录或 Git Worktree 时，业务执行才进入项目外的另一目录。
3. 规划 Agent 根据任务提出节点、依赖、模型、写入范围与验收要求。查看计划后批准执行。
4. 独立且范围不冲突的节点可以并行；需要上游成果的节点等待依赖完成。
5. 任务完成后查看变更与验收结果，并回到同一任务继续对话。

模型之间交接目标、来源、用户约束和成果，不互相复用原生会话 ID。较早的用户要求保存在脱敏原文台账中，Agent 可以按引用或关键词读取；助手的推断不会自动变成用户授权。老数据只有历史摘要时，系统不会声称找回了不存在的完整原文。

## 运行中询问和调整

- **询问**：查看已有进度快照，不暂停调度，也不改计划。进度类问题由系统直接回答；需要解释时使用无工具的快照问答。回答带有快照时间与版本，不能代表回答期间新发生的情况。
- **调整**：先暂停启动新节点，等待当前节点到达安全检查点，再生成候选计划。查看复用、重跑、新增和删除范围，批准后继续。
- **恢复**：系统重新核对相关文件证据。仍有效的成果可以复用；输入或产物被外部修改、缺少必要证据时进入待处理状态，保留现有文件。
- **副作用**：命令和外部工具不能仅凭项目文件快照证明可安全重复。存在不确定副作用或连续恢复没有进展时，系统停止自动重放，等待用户检查。

## 验收方式

| 方式 | 行为 |
| --- | --- |
| 标准 | 新计划默认。单节点直接复用节点成果作为候选并做独立语义验收；多节点继续整合与验收。 |
| 严格 | 保留独立 Integrator 与 Validator 两个阶段；旧计划缺少策略字段时保持此方式。 |
| 机器验收 | 仅在用户明确批准且所有验收标准都有宿主命令证据、没有语义风险或跨节点依赖等条件时使用。条件不足自动保留语义验收。 |

所有方式均保留计划审批、真实文件校验、写入范围检查和宿主命令证据。研究、写作和综合判断不会仅因字段齐全就直接判定成功。

## 文件与恢复边界

计划、日志、检查点和控制协议存放在工作台数据目录，业务成果按任务约定留在项目中。`writeScope` 用于调度、权限提示和事后核查，不等于操作系统沙箱。

当前 Codex、Claude 原生适配器没有承诺完整暴露所有隐式文件读取，因此输入变化检测仍采用保守工作区快照。未来适配器只有明确证明读取完整可观测时，才能缩小读取依赖；未知工具、命令、会话恢复或外部能力都回退保守检测。明确登记的目录产物仍检查完整内容，包括通常在源码扫描中忽略的目录。

## 与委派模式的关系

[委派协议](delegation.md)适合一次对话里的动态主脑与子 Agent 协作。编排则负责已批准计划的依赖、持久状态与验收。两者共享底层执行能力和任务上下文，保留各自状态机。

当前编排节点不能再自行启动嵌套 Agent 或调用委派桥；需要分工时应由计划显式增加节点并经过审批。原生对话与协作模式仍提供各自声明的子 Agent 能力。

简单问答、探索性需求或小修改通常使用普通对话更高效。编排的价值在于复杂任务的可恢复交付，不在于把每一步都拆成节点。
