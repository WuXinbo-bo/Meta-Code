# 委派协议

委派协议是 Meta Code 普通对话中的协作能力。它让一个 Agent 保持主脑角色，同时调用其他已连接 Agent 完成边界清晰的子任务。

它解决的不是“同时打开多个聊天”，而是让跨 Provider 协作拥有统一的任务边界、权限、实时日志、失败状态、文件 Diff 和验收结果。无论执行者来自 Codex、Claude、Gemini 或后续 ACP Agent，主脑看到的都是同一套工作台任务合同。

## 工作方式

1. 用户选择主脑，并把运行模式切换为“协作”。
2. 主脑分析任务，选择适合的子 Agent，并声明工作目录、任务范围、权限、验收标准和输出要求。
3. 工作台建立独立子会话，实时归一化命令、工具、文件 Diff、失败、取消和最终结果。
4. 主脑读取子 Agent 结果，检查文件改动与测试；不合格时可以继续委派修复。
5. 主脑统一向用户回复，子 Agent 不直接取代主脑的最终交付。

## 界面中会看到什么

- 聊天输入区显示当前为“协作”模式，主脑 Provider 与模型仍独立选择。
- 每个子任务显示实际执行 Agent 的图标、状态、命令、工具调用和文件改动。
- 失败、取消与重试归属于对应子任务，不会混入主脑回复。
- 主脑最终回复只负责综合结论；子 Agent 的原始过程仍可单独检查。

## 与原生模式的关系

原生模式直接使用当前 CLI，并保留其原生子 Agent 和会话能力。协作模式增加的是工作台级跨 Provider 委派；它不会假定所有 CLI 都支持相同的原生子 Agent 协议。

## 与任务编排的区别

委派适合连续对话中的临时拆分，结构可以随对话变化。任务编排适合长时间、强依赖、明确交付物的复杂工作，它会保存独立计划、节点 DAG、审批状态和机器验收结果。

当一个需求已经需要预先确定多个阶段、限制并发写入、暂停后恢复或逐项验收时，不要继续把所有步骤堆在一次对话里，应改用 [Meta 任务编排](task-orchestration.md)。

## 使用建议

- 子任务应可以独立理解和验证。
- 多个可写子任务不要并发修改同一批文件。
- 验收标准尽量包含可执行测试或明确文件产物。
- 涉及危险命令、工作区外写入或密钥时使用按需审批。
- 在主脑交付前检查子 Agent 日志和 Diff，而不是只看自然语言结论。
